# Architecture

This is the depth behind the summary in [`AGENTS.md`](../AGENTS.md), read on demand: before changing any workflow, capability or generator skill, the review gate, or a reviewer agent. `AGENTS.md` stays under the org's 32 KiB guidance budget, so the two architectures live here.

## How the pieces fit together

Two non-obvious architectures live in this repo.

### Generator + capability skills (the dev-workflow family)

- **The six workflow skills are generic and ship in the plugin.** `survey-work` (work plate), `groom-backlog`, `take-it` (parallel issue-shipping), `dispatch-ready` (loop dispatcher), `send-it` (single-PR end-to-end) and `tidy-repo` each have exactly ONE implementation under `skills/`. Per-repo behaviour lives in that repo's `.claude/sassy-dog/<skill>.md` config, read at load time via dynamic context injection; the format is `setup-config/references/config-contract.md`. **There is no per-repo copy** — that is what makes every invocation render namespaced and removes the trigger-phrase competition the earlier generated-skills design had to work around.
- **`NO_CONFIG` is a first-class state.** A skill invoked in a repo with no config MUST derive what it safely can and run in its most conservative mode. Of the six, two block instead, because both act unattended and outward-facing: `take-it` and `dispatch-ready`. The two dispatch front-ends below (`work-recommendations`, `work-fire-watch`) inherit that stop from `take-it.md` and block too — four stoppers in all.
- **Configure only what cannot be derived.** Repo slug, default branch and `delete_branch_on_merge` come from `gh repo view` at runtime and never appear in config — a configured value is a value that can drift. `review_site:` is a deliberate exception; the justification sits beside the key in the contract.
- **Workflow skills are thin and delegate.** Shared mechanics live in the capability skills — `github-issues`, `sentry-triage`, `pr-shepherd` (polling, merge queue, coupled-PR serialization, worktree teardown, the serial-checkout guard, and the platform-degradation probe that gates nothing), `repo-cleanup`, `repo-health`, `testflight` — invoked by namespaced name. Fix mechanics in the capability skill, never in a workflow skill. `repo-cleanup` keeps its name as a capability-boundary distinction (mechanics vs. the user-facing `tidy-repo` flow), not the trigger-collision avoidance it was first named for.
- **A consumer repo that tracks `.claude/settings.json` must declare BOTH the marketplace and the plugin**: `extraKnownMarketplaces` (where the `skills` marketplace lives) and `enabledPlugins` (`"sassy-dog@skills": true`). `enabledPlugins` alone is **not** sufficient locally — it references the marketplace by name only, and registration otherwise lives in user-level state ([#97](https://github.com/Sassy-Dog/skills/issues/97)). **Tracking the file is a per-repo choice for local multi-machine convenience and does not reach cloud sessions or routines** ([#468](https://github.com/Sassy-Dog/skills/issues/468)): per the Claude Code docs (plugins/install, plugins/loading, cloud-environments) a cloud session loads neither user-scope plugins nor the ones a repo's `.claude/settings.json` turns on, so #97's premise that the declaration fixed cloud loading was wrong (consistent with #144's conclusion and #175). For a public repo the **default** is to track only `.claude/sassy-dog/*.md` and keep `settings.json` and `hooks/` local — project hooks run without a trust prompt in several modes — and **committed** is a choice the user may make. The tracking choice is part of the plan the user approves in every mode that writes `settings.json` (`setup-config` SKILL.md, "Tracking choice in the plan", owns the mechanics): one of two end states, **local** (public default) or **committed**, each with an exact `.gitignore` shape and tracked/ignored status, and `skills/setup-config/scripts/tracking-state.sh` owns the derive and transition rules (`derive`, `plan`, `apply` with a required plan-id and a re-derive before it acts, `verify`; a failed git probe exits 2 "unknown, not verified" and never reads as ok; the section's table is documentation, the script is authoritative, and `test-tracking-state.sh` enumerates its rows). The state is derived from every fact that defines it (the lines and their order, `settings.json` and each owned `sassydog-*.sh` tracked and ignored status, the sassy-dog negation), so a matching state proposes nothing and a mixed one is reported and moved to the target; owned scripts are direct-child regular files with a safe name, and a hostile name, a nested path under an owned-name entry or a symlinked `.gitignore` is reported or refused, never acted on; `apply` refuses before its first write (exits 6, 7 and 8; the script header's exit table is the authority) while a non-regular `.gitignore`, an unsafe, nested, directory or symlinked owned-name entry, or an ignore rule outside the managed lines (a nested `.gitignore`, `.git/info/exclude`, `core.excludesFile`) exists, and the human renames, removes or edits it (the script never deletes a user file or edits a rule it does not own); the committed shape also ignores non-owned hooks and owned-name directories, so `git add -A` does not stage them, but in a repo that is ALREADY committed an unsafe-named or symlinked `sassydog-*.sh` entry is reported as mixed and the glob does NOT keep it out of `git add -A`, and `.claude/*` is never narrowed or dropped. Untracking warns that collaborators' copies are deleted on pull. `setup-hooks` calls the script for what it renders, defaults to `settings.local.json` (local) in a public repo and moves its owned entries in either direction rather than duplicating them, `setup-repo` asks the choice once (`local` or `committed`) and passes it to both generators, and `setup-config` Phase 7 step 2 verifies the result and carries the reasoning ([#472](https://github.com/Sassy-Dog/skills/issues/472)). This repo is public and follows that default: since 2026-10-07 it tracks only its `.claude/sassy-dog/*.md` configs, and its own `.claude/settings.json` plugin declaration is local and ignored (`.claude/*` + `!.claude/sassy-dog/`). The declaration never reached cloud sessions anyway, and it never installed the plugin for a contributor who lacked it: this marketplace's plugin entry uses a `github` source, so such a contributor got a `/plugin` Errors-tab row instead, plus a background clone of the marketplace on accepting the trust dialog (`setup-config` Phase 7 step 2).
- **Routine prompts carry a skill-load fallback as contract, and its degraded-load signal is a REQUIRED FIELD, never a discretionary sentence.** A scheduled routine **cannot load a plugin skill at all** — there is no supported mechanism ([#175](https://github.com/Sassy-Dog/skills/issues/175)), so the clause is the only thing making these routines work. A "note the degraded load" sentence is discretionary and **has already been dropped in a live run**, which then delivered a complete, authoritative-looking report with no note: a missing sentence reads as fine, an empty slot in a structured header reads as broken. So both report skills render an always-present `Load: plugin | fallback (degraded)` header field and the routine clause names it. **The field is still the run reporting on itself — where the report and the run log disagree, the log wins**; the out-of-band `Unknown skill:` check is [`ROUTINES.md`](ROUTINES.md). Clause shape for any new routine: skill name + its `skills/<name>/SKILL.md` path + the `Load:` field.
- **`work-recommendations` and `work-fire-watch` are dispatch front-ends with one loop between them, and deliberately NO config template.** `work-fire-watch` fetches the newest `daily-fire-watch` post from Slack (read-only, tools resolved by capability, only the pinned poster id counts), reads **only the `fire-watch-v1` machine block** the routine appends — the delivered prose is mrkdwn that changes shape day to day and is never parsed; the producer resolves the product→repo map, so routing is one exact `repo` match — and delegates the numbered list to `work-recommendations`, which resolves each item to a handle, files the issue-less ones through `file-or-link-issue.sh` behind one preview (markers `sentry-source:`, `plate-source:`, `fire-watch-source:` — a closed list), and makes one ordered `take-it` call. Neither has a `.claude/sassy-dog/<name>.md`: both read `take-it.md` only (stopping on `NO_CONFIG` *before* filing anything), so a later "every workflow skill gets a template" sweep should not add one. Nothing pins that absence — a sweep that adds a template *and* its inventory row passes `test-doc-reconciliation.sh` §7 green — which is why it is recorded here. A security finding is human-only in both — the plate's `rotate and revoke` line, and on the fire-watch path the `auto-security-watch` issue that `security-watch.yml` files (the routine's edition has no Security section — its `whats-on-fire` §3E says so, and the block's `security` tier is that edition's "Security, always listed" group; `work-recommendations` reads every `#N`'s live labels before dispatch, and a failed read is HOLD). One approval per run covers filing and dispatch, since neither `take-it` nor `pr-shepherd` asks again. Neither re-runs `whats-on-fire`; a missing or "could not run" post is a stop. **The producer `work-fire-watch` reads is the flattened copy in `routines`** (`Daily Fire Watch (…)`, not this repo's `# What's on fire (…)`); its sentinels and the block spec are listed in [`ROUTINES.md`](ROUTINES.md), `test-fire-watch-block.sh` pins them on this side, and that repo's CI is where a producer-side gate can live (it can clone this one; this one cannot clone it).
- **`setup-config` is a config generator, not a runtime skill.** Run inside a product repo it writes `.claude/sassy-dog/*.md` plus the `.claude/settings.json` plugin declaration, and renders no skill bodies. Modes: **migrate**, **update**, **adopt**, **create**. Siblings `setup-hooks` and `setup-deps` follow the same generator pattern.
- **`setup-repo` is the umbrella orchestrator over those three and carries no generation logic.** It picks which generators apply, prints one combined plan of every file they would touch, gets approval, then runs them **strictly in sequence** (`setup-config` → `setup-hooks` → `setup-deps`) and reports what ran and what was skipped — a skipped generator is a reported outcome, never a silent no-op. **The order is load-bearing**: `setup-config` and `setup-hooks` both write `.claude/settings.json`, merging surgically into their own keys, so sequential runs compose while a concurrent or last-write-wins run drops one *silently* (a prior migration lost a consumer's `PreToolUse` push guard exactly this way). **Never dispatch the generators as parallel sub-agents.** Generation mechanics stay in the generators, **never** in the orchestrator.
- **One delegation mode.** Independent/vendored mode was removed — it was the only path that could produce an unbranded, un-namespaced skill. Everything delegates `Skill: sassy-dog:<cap>`.
- **`setup-hooks` is the same generator pattern one layer down.** It detects the consumer's stack (keyed on repo config presence, never installed binaries) and renders a PostToolUse formatter/linter dispatcher plus an always-rendered stray-artifact guard, with their settings entries. The guard also owns a matcher-less `Stop` entry and ensures `/tmp/` is gitignored — a guard whose destination is not ignored only relocates the mess. **Its two ownership markers behave differently under a rename**: the settings entry is owned by command path (`.claude/hooks/sassydog-`), which no producer rename touches; the script is owned by its `generated-by:` producer name, committed inside every consumer repo — so the matcher must accept every producer name this generator has emitted across both marker namespaces, or every pre-rename script is classified hand-written and skipped *silently*. Re-runs reconcile only owned entries. Pinned by `test-ownership-matchers.sh` and `test-detect-hook-stack.sh`.
- **The two generators' render invariants are deliberately DIFFERENT, and neither should be restated as the other's.** `setup-hooks` stays **deletion-only** — one hook script per repo, so every render is valid by construction. `setup-deps` is **validated after render** ([#169](https://github.com/Sassy-Dog/skills/issues/169)): a Dependabot lane is an (ecosystem, **directory**) pair and a monorepo needs the same ecosystem at several directories, which deletion cannot express — so the template repeats a block per location and `validate-dependabot.sh` asserts every emitted `directory:` actually holds the manifest it claims. That trade is strictly stronger here, because the static guarantee never caught the bug: a bad render was always valid YAML pointing at directories with no manifests, and Dependabot answers that by silently doing nothing. `render-dependabot.sh` refuses to default a lane to `/`, and `--compare-to` catches the diverged-but-owned file rather than overwriting it. The optional per-ecosystem `cooldown` ([#498](https://github.com/Sassy-Dog/skills/issues/498)) rides that same path: `--cooldown ECOSYSTEM=DAYS` goes to both the renderer and the validator, the cooldown is purely additive (a render without it carries none of it, and one with it differs only by the cooldown blocks, their header paragraph and the stamp), and a cooldown the validator was not told about is divergence, not something to tolerate: `--change-cooldown ECOSYSTEM` acknowledges a deliberate change or removal per ecosystem and requires `--compare-to`, while a forgotten `--cooldown` still fails closed ([#501](https://github.com/Sassy-Dog/skills/issues/501)). Hand-added `ignore:` rules take the same path ([#508](https://github.com/Sassy-Dog/skills/issues/508)): `render-dependabot.sh --keep-ignores-from` carries the committed file's rules into the render, and `--compare-to` fails every rule a render drops, so a forgotten flag cannot strip a hold. A lane the render ADDS fails `--compare-to` as `DIVERGED` too, since a repo's deliberate absence of a lane is otherwise unprotected; `--accept-added-lane ECOSYSTEM:DIRECTORY` acknowledges exactly one pair, mirrors `--change-cooldown` (needs `--compare-to`, refused where the render adds no such pair), and is passed only after the human approved that lane as a plan item. Pinned by `test-dependabot-render.sh`.
- **Config format: frontmatter is regenerated, `##` prose is carried across verbatim.** That split is the point — prose is what a refresh must never rewrite. Contract: `setup-config/references/config-contract.md`. **The split assumes frontmatter is *derived*, and several keys are not**; the exceptions are enumerated in `setup-config/SKILL.md`'s guardrail list, which is the copy to trust — do not read this sentence as a closed set. `gotcha_summary` is unbounded free prose in a frontmatter slot, recomputed by nothing, so its rule is **invariants only** — never an issue number with a state claim, an "as of `<date>`", or a roadmap position — enforced where it is *used*: `groom-backlog` injects only what `verify-gotcha-claims.sh` confirms against live issue state (`test-gotcha-claims.sh`). **Marker recognition must accept every producer name and both marker namespaces**; an unrecognised marker drops the repo into create mode and silently loses its config.
- **Write paths are concentrated.** `skills/github-issues/scripts/file-or-link-issue.sh` is the single issue-creation path (marker-keyed idempotency, `--dry-run`, preview-then-confirm, burst rail). That idempotency is **two stages, and neither is redundant** ([#339](https://github.com/Sassy-Dog/skills/issues/339)): the search index is unbounded in *age* but **asynchronous** — a marker re-run seven seconds after filing searched, got `[]`, and filed a duplicate — while a `--search`-less `gh issue list` is a direct object read, read-after-write consistent but bounded to the newest `--recent-scan` issues. **Both stages match the delimited footer `<!-- <marker> -->` through one predicate**, and applying it to one stage is not enough for two different reasons: the scan's `contains()` is a substring test, while GitHub phrase search matches a token *subsequence* — so `epic-split: #207/alpha` hits a sibling `#207/alpha-two`, and the search route fires on the sibling that is already indexed, which is the ordinary case. That harm is quieter than #339's own: a real epic child never filed, reported as `already-linked`. `test-file-or-link-issue.sh` is what stops a later "one lookup is enough" sweep dropping either half. `sentry-triage` never mutates Sentry. Keep it that way.

### Orchestrator + reviewer agents (`assess-it` and `pr-review-orchestrator`)

The nine `*-reviewer` agents have **two dispatchers and two modes**, and the modes are the whole design. Understanding either one means reading its orchestrator alongside the reviewers: `skills/assess-it/SKILL.md` + `orchestration.md` for audit mode, `agents/pr-review-orchestrator.md` for diff-scoped mode.

- **`assess-it` is the audit-mode orchestrator.** Six phases: detect stack → fan out reviewer agents concurrently (one message, multiple Agent calls) → adversarially verify each finding → cluster into PR-sized work → preview and file GitHub Issues under a tracking Epic → report, coverage included. The file numbers them `Phase 0`–`Phase 5`; where the two disagree about labels, trust the file.
- **Audit mode scores a lost reviewer too, and the consequence lands at the PREVIEW rather than in a report** ([#284](https://github.com/Sassy-Dog/skills/issues/284)). This is the **sibling** of the diff-scoped `!` rule, not a copy — and the asymmetry a later "align the two modes" sweep will flatten is the point: a diff-scoped hole is read in-session and costs a re-run, while **audit mode writes**, so a lost `security-reviewer` yields a filed Epic that omits a whole domain and **reads complete** to every later reader. Phase 1 records a four-outcome ledger per domain (`returned` / `no report` / `could not dispatch`, plus `not dispatched` for a domain skipped for cause, kept visibly apart from the two dark ones); a domain that is not `returned` is **dark** and is never scored clean. Phase 4 prints the ledger **before** the approval prompt, Phase 5 reprints it, and **the Epic body carries it too** ([#294](https://github.com/Sassy-Dog/skills/issues/294)) — the durable half, since preview and report are session output reaching only the person who approved the filing. `assessment-rubric.md` carries an **abstain** value, because a table demanding a number from a dark domain makes an agent invent one, and an invented score is worse than a missing one precisely because it looks measured and it sorts. **It is surfaced, not a veto** — filing still proceeds on approval, and both halves are pinned by `test-audit-lost-reviewer.sh`.
- **`pr-review-orchestrator` is the diff-scoped orchestrator** (`agents/pr-review-orchestrator.md`), dispatched by `send-it`'s review gate before the PR body is drafted. It reads the diff versus the *derived* default branch (never an assumed `main`), or versus a caller-supplied, validated `base_override` commit when a coordinator reviews only a nit roll-in delta (the one exception, with no silent fallback: `take-it` §6 defines the roll-in, the orchestrator's Step 1 the input), classifies changed paths into surfaces, fans out **only to touched surfaces**, runs its own integration-check pass for cross-surface concerns no single specialist sees, and returns one report split into **Blocking** vs **Nits**. It dispatches **only the nine reviewers this plugin ships** — the design it replaced named user-level agents, and a plugin default that fans out to an agent a consumer repo lacks fails the entire review rather than degrading, while resolving fine on the author's own machine ([#236](https://github.com/Sassy-Dog/skills/issues/236), pinned by `test-review-orchestrator-allowlist.sh`). Adding a tenth dispatch target means shipping that agent here first.
- **Two config keys carry that gate, and the settled decisions governing it are enumerated in the opening section of [`AGENTS.md`](../AGENTS.md) (`## What this repo is`).** **`review_agent:`** resolves the shipped orchestrator when absent, so no `send-it` run can silently ship unreviewed; the opt-out is the explicit `review_agent: skip`. **`review_site: agent | coordinator`** chooses whether each dispatched sub-agent reviews its own diff **before** opening its PR or the dispatching loop reviews each PR **after** it opens — because `take-it` and `dispatch-ready` open PRs from cold worktrees without invoking `send-it`, and a gate living only in `send-it` never runs for the two paths carrying most of the repo's PR volume ([#248](https://github.com/Sassy-Dog/skills/issues/248)). An absent key selects `coordinator`, for cost: under `agent` every worker ran the full reviewer fan-out itself once per fix round, while every PR is reviewed before merge either way. A repo can steer classification without owning an agent via the optional **`review_surfaces:`** glob → reviewer map ([#238](https://github.com/Sassy-Dog/skills/issues/238)): its values are only those nine, it is **additive** — no form of it removes a reviewer, so it cannot under-dispatch — and an unresolvable value discards the whole map and returns a Blocking finding while the built-in table reviews the diff meanwhile. It steers surface classification alone.
- **A review report is RETURNED as the reviewing agent's final text, never sent to a session** ([#273](https://github.com/Sassy-Dog/skills/issues/273)): delivery needs an address the reviewer cannot reliably resolve, and of five measured occurrences not one report reached the dispatching session — every one that arrived did so because a human relayed it. All three shipping paths read the returned text themselves and never block while a dispatched review is outstanding. A dispatch that ran but produced no usable report is `review: NO REPORT`, never `review: SKIPPED`, which claims no agent ran. `take-it` and `dispatch-ready` hold that PR on either review site; `send-it` records the degraded outcome and continues its operator-facing flow. The reviewer→orchestrator hop is bound the same way ([#280](https://github.com/Sassy-Dog/skills/issues/280)): each of the nine states the full rule, and the delivery rule is a **member** of the fan-out brief, whose list stays **closed** — closedness is what stops a brief re-authoring a reviewer's checklist. None of it retires Step 5's lost-reviewer reporting bullet: a clean fan-out is not evidence the hop worked, so read the `!` count.
- **Parent recovery belongs only to the shipped PR orchestrator** ([#385](https://github.com/Sassy-Dog/skills/issues/385)); its single definition is `### Parent recovery protocol` in `agents/pr-review-orchestrator.md`. Normal nested fan-out stays the default. Explicit plan-only or inability to dispatch nested reviewers returns a `review-fanout-plan`, not a report; only the actual caller can run a missing/unusable-only concurrent batch and submit complete actual returns and failures to `aggregate-only`. Changeset/context identity gates every reuse, and aggregation still performs the whole-diff integration pass without rerunning successful specialists. The batch plus aggregation shares the existing single automatic recovery allowance with failed checks and Blocking findings.
  **Report-only recovery** ([#386](https://github.com/Sassy-Dog/skills/issues/386)) uses that same allowance at most once when the shipped orchestrator returned only a correction, tally or partial text: normal and compact-clean reports are already complete. With identical changeset/context and the actual returned dispatch handle/agent identity, the caller may request only the already-completed full human report, never re-analysis, fan-out, an integration pass, a relay or file pointer. It retains enumerated Blocking findings and dark coverage unless that full report explicitly supports their correction; changed input, an unreachable handle, spent/unknown allowance or another fragment stays NO REPORT, never clean.
  Recovery accounting accepts only authenticated workflow-owned records bound to the actual attempt. `send-it` defines a branch-keyed checkpoint under the Git common directory for pre-PR work with no linked issue, then transfers its state into the PR body; `dispatch-ready` persists pending reservations before the scheduling tick ends.
  Exhausted pre-PR failures use `take-it` §5's authenticated issue-only terminal handoff. Both coordinators consume it before PR filtering; active-attempt identity prevents stale demotions, and only confirmed blocking frees capacity. Absence of a PR or spent recovery alone is never a terminal outcome.
- **The `*-reviewer` agents are the fan-out workers for both.** Each owns a domain (architecture, code-quality, security, testing, cicd-release, infra-platform, observability-ops, dx-docs, dependency-supply-chain) and in **either** mode it FINDS problems and cites `file:line` evidence, never writing code. Audit mode sweeps the repo and asks "what is wrong here"; diff-scoped mode is handed a changeset and asks "does this diff introduce a regression", bounded to the changed hunks and their blast radius. The audit dispatch map lives in `orchestration.md`, the diff-scoped surface map in the orchestrator. Each reviewer's `## Diff-scoped mode` section is a sibling of its audit-mode declaration, not a replacement.
- **All agents return the same finding schema in BOTH modes** (title, area, severity, likelihood, evidence, why_it_matters, proposed_fix, acceptance, pr_size, labels, confidence). The return transport is the JSON object `{"findings": [...]}`; `{"findings": []}` is a completed empty review, and missing or malformed envelopes are unusable, never clean. One transport form beyond a bare object is usable: exactly one fenced block (` ```json ` or bare ` ``` `) with only whitespace outside it, held to the same schema check; prose outside the object, two or more fences and an unterminated fence stay unusable, identically in both consumers. Reviewers must still return a bare object; the tolerance exists only so a completed review is not discarded. Both consumers unwrap the array; the final human PR report stays Markdown. That is what lets one set of reviewers serve two orchestrators, so it is the invariant to protect: keep any edit to one reviewer's output contract consistent with `orchestration.md` and the others, and never let a mode grow a field of its own. Blocking-vs-Nits is a *derivation* the PR orchestrator performs from `severity`, `confidence` and a policy citation the finding's own `evidence` carries — reviewers do not pre-split, and the orchestrator never promotes on an impression the schema cannot express.
- `github-secrets` and `testflight` are standalone capability skills — no agent orchestration.
