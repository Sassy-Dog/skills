# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A **Claude Code plugin marketplace** containing a single plugin (`sassy-dog`) that bundles reusable skills and review agents for Claude Code, Gemini CLI, and other AI coding tools. Repo visibility is **`PUBLIC`** — a deliberate exception to the org's `INTERNAL` default, taken on 2026-08-12 because the claude.ai account-level plugin marketplace **cannot sync a non-public repo** (a non-public source fails with `Marketplace sync failed` regardless of org app install or SSO state; see [#175](https://github.com/Sassy-Dog/skills/issues/175)). Two consequences follow and must not be undone by a later "align with the org default" sweep: org secrets with `private` visibility do not reach this repo (that is *desirable* here — see [#178](https://github.com/Sassy-Dog/skills/issues/178)), and CI runs on GitHub-hosted runners rather than the self-hosted fleet, because `on: pull_request` fires for fork PRs. Licensed Apache-2.0.

There is **no build step** — the entire repo is Markdown (skills/agents) plus the Bash scripts bundled inside skills' `scripts/` directories. CI (`.github/workflows/ci.yml`, required on `main`) runs `bash scripts/preflight.sh` — the single source of truth for every gate: shellcheck, `scripts/check-frontmatter.sh` (loader requirements on every tracked skill/agent file, plus the Agent Skills spec constraints on `SKILL.md` alone), the positional-token and legacy-name guards, manifest JSON validation, the CalVer version-of-record guard, markdownlint (`.markdownlint-cli2.jsonc`), and the 47 `scripts/test-*.sh` gates. **Run `bash scripts/preflight.sh` locally before every PR** (`--fix` auto-fixes markdownlint findings).

**Each gate's rationale lives in its own script header. Read it there; never restate it here.** Those headers are load-bearing prose rather than commentary — nearly every one records a decision that *reads* like drift, an inconsistency, or dead weight and is deliberate, together with the mutation proving the gate is not vacuously green. Before editing a gate, or the `SKILL.md` prose a gate pins, read that header first, and never delete a rule merely because it looks inconsistent with a governing principle stated elsewhere: that specific edit is what most of these gates exist to stop. This paragraph replaced a 118 KB transcription of those headers which had already drifted — it documented 24 of the 27 gates that existed when it was removed — and which was the same third-copy shape this repo refuses for its label taxonomy (`test-label-taxonomy.sh`), turned on its own documentation. Nothing enforces that here, which is exactly why it grew.

The shipped orchestrator's recovery checks bind actual caller sites, complete identity/provenance, missing-only dispatch and aggregate-only boundaries; and 7. the nine reviewers deliver to the orchestrator the same way, the delivery rule riding as one member of a fan-out brief whose list stays closed. Source-level and flattened; twenty-one tracked files, no `gh`, no network).

Four rules have **no gate of their own**, so nothing fails when they are undone:

- **shellcheck runs twice, and the second pass is not redundant.** The tree-wide run is `-S warning`; SC2006 is `style`, so that run cannot see it, and a second pass exists for SC2006 alone. Do not fold them together — an unescaped backtick inside a double-quoted string is command substitution, and this gap shipped the same defect twice (three test labels in `test-sentry-verification.sh` were silently executing `which`, `that` and `where`). A bespoke grep was tried and rejected: 3 true positives against 7 false, because a backtick inside a single-quoted string is a different question that only a shell parser answers.
- **actionlint is CI's own step, not preflight's, and that split is forced.** In CI, two separate steps run a pinned native binary (never the dockerized action): the bare tree-wide run, and the rendered-template gate. `ci.yml` puts that binary on `$GITHUB_PATH`, which reaches only *later* steps, while preflight runs before the install — so preflight skips both in CI and runs them locally when `actionlint` is on `PATH`, falling back to the pinned `rhysd/actionlint` image when it is not. That local docker fallback is the only linting a contributor without the binary gets; do not delete it as redundant with CI.
- **actionlint lints the workflow templates' embedded `run:` blocks, but ONLY because shellcheck is already on `PATH` when it runs.** actionlint's shellcheck integration is what covers that shell, and nothing anywhere asserts the ordering: `ci.yml`'s `Install shellcheck (pinned + sha256-verified)` step puts it on `$GITHUB_PATH`, and `actionlint (setup-deps workflow templates)` is a later step that inherits it. Reorder those two and the highest-consequence YAML in the tree silently stops being shell-linted while CI stays green.
- **Green is necessary, not sufficient.** "Correctness" still means accurate trigger phrases and skill instructions that actually work when invoked. Verify by installing the plugin locally (below) and exercising the skill.

## Layout (flat — everything at root)

This repo *is* the plugin; there is no nesting under a plugin subdirectory.

```
.claude-plugin/
  plugin.json        # plugin manifest — version is the version-of-record, stamped by scripts/stamp-version.sh (never hand-edit)
  marketplace.json   # marketplace entry pointing at the GitHub repo
agents/
  *-reviewer.md      # subagents, auto-discovered, namespaced sassy-dog:<name>
  pr-review-orchestrator.md  # diff-scoped fan-out over the nine reviewers
skills/
  <skill>/
    SKILL.md         # required: frontmatter (name + description) + instructions
    references/      # optional: deep reference docs (progressive disclosure)
    scripts/         # optional: executable tools the skill calls
```

## How the pieces fit together

Two non-obvious architectures live in this repo.

### Generator + capability skills (the dev-workflow family)

- **The six workflow skills are generic and ship in the plugin.** `survey-work` (work plate), `groom-backlog`, `take-it` (parallel issue-shipping), `dispatch-ready` (loop dispatcher), `send-it` (single-PR end-to-end) and `tidy-repo` each have exactly ONE implementation under `skills/`. Per-repo behaviour lives in that repo's `.claude/sassy-dog/<skill>.md` config, read at load time via dynamic context injection; the format is `setup-config/references/config-contract.md`. **There is no per-repo copy** — that is what makes every invocation render namespaced and removes the trigger-phrase competition the earlier generated-skills design had to work around.
- **`NO_CONFIG` is a first-class state.** A skill invoked in a repo with no config MUST derive what it safely can and run in its most conservative mode. Of the six, two block instead, because both act unattended and outward-facing: `take-it` and `dispatch-ready`. The two dispatch front-ends below (`work-recommendations`, `work-fire-watch`) inherit that stop from `take-it.md` and block too — four stoppers in all.
- **Configure only what cannot be derived.** Repo slug, default branch and `delete_branch_on_merge` come from `gh repo view` at runtime and never appear in config — a configured value is a value that can drift. `review_site:` is a deliberate exception; the justification sits beside the key in the contract.
- **Workflow skills are thin and delegate.** Shared mechanics live in the capability skills — `github-issues`, `sentry-triage`, `pr-shepherd` (polling, merge queue, coupled-PR serialization, worktree teardown, the serial-checkout guard, and the platform-degradation probe that gates nothing), `repo-cleanup`, `repo-health`, `testflight` — invoked by namespaced name. Fix mechanics in the capability skill, never in a workflow skill. `repo-cleanup` keeps its name as a capability-boundary distinction (mechanics vs. the user-facing `tidy-repo` flow), not the trigger-collision avoidance it was first named for.
- **A consumer repo that tracks `.claude/settings.json` must declare BOTH the marketplace and the plugin**: `extraKnownMarketplaces` (where the `skills` marketplace lives) and `enabledPlugins` (`"sassy-dog@skills": true`). `enabledPlugins` alone is **not** sufficient locally — it references the marketplace by name only, and registration otherwise lives in user-level state ([#97](https://github.com/Sassy-Dog/skills/issues/97)). **Tracking the file is a per-repo choice for local multi-machine convenience and does not reach cloud sessions or routines** ([#468](https://github.com/Sassy-Dog/skills/issues/468)): per the Claude Code docs (plugins/install, plugins/loading, cloud-environments) a cloud session loads neither user-scope plugins nor the ones a repo's `.claude/settings.json` turns on, so #97's premise that the declaration fixed cloud loading was wrong (consistent with #144's conclusion and #175). For a public repo the **default** is to track only `.claude/sassy-dog/*.md` and keep `settings.json` and `hooks/` local — project hooks run without a trust prompt in several modes — and **committed** is a choice the user may make. The tracking choice is part of the plan the user approves in every mode that writes `settings.json` (`setup-config` SKILL.md, "Tracking choice in the plan", owns the mechanics): one of two end states, **local** (public default) or **committed**, each with an exact `.gitignore` shape and tracked/ignored status, and `skills/setup-config/scripts/tracking-state.sh` owns the derive and transition rules (`derive`, `plan`, `apply` with a required plan-id and a re-derive before it acts, `verify`; a failed git probe exits 2 "unknown, not verified" and never reads as ok; the section's table is documentation, the script is authoritative, and `test-tracking-state.sh` enumerates its rows). The state is derived from every fact that defines it (the lines and their order, `settings.json` and each owned `sassydog-*.sh` tracked and ignored status, the sassy-dog negation), so a matching state proposes nothing and a mixed one is reported and moved to the target; owned scripts are direct-child regular files with a safe name, and a hostile name, a nested path under an owned-name entry or a symlinked `.gitignore` is reported or refused, never acted on; `apply` refuses before its first write (exits 6, 7 and 8; the script header's exit table is the authority) while a non-regular `.gitignore`, an unsafe, nested, directory or symlinked owned-name entry, or an ignore rule outside the managed lines (a nested `.gitignore`, `.git/info/exclude`, `core.excludesFile`) exists, and the human renames, removes or edits it (the script never deletes a user file or edits a rule it does not own); the committed shape also ignores non-owned hooks and owned-name directories, so `git add -A` does not stage them, but in a repo that is ALREADY committed an unsafe-named or symlinked `sassydog-*.sh` entry is reported as mixed and the glob does NOT keep it out of `git add -A`, and `.claude/*` is never narrowed or dropped. Untracking warns that collaborators' copies are deleted on pull. `setup-hooks` calls the script for what it renders, defaults to `settings.local.json` (local) in a public repo and moves its owned entries in either direction rather than duplicating them, `setup-repo` asks the choice once (`local` or `committed`) and passes it to both generators, and `setup-config` Phase 7 step 2 verifies the result and carries the reasoning ([#472](https://github.com/Sassy-Dog/skills/issues/472)). This repo is public and follows that default: since 2026-10-07 it tracks only its `.claude/sassy-dog/*.md` configs, and its own `.claude/settings.json` plugin declaration is local and ignored (`.claude/*` + `!.claude/sassy-dog/`). The declaration never reached cloud sessions anyway, and it never installed the plugin for a contributor who lacked it: this marketplace's plugin entry uses a `github` source, so such a contributor got a `/plugin` Errors-tab row instead, plus a background clone of the marketplace on accepting the trust dialog (`setup-config` Phase 7 step 2).
- **Routine prompts carry a skill-load fallback as contract, and its degraded-load signal is a REQUIRED FIELD, never a discretionary sentence.** A scheduled routine **cannot load a plugin skill at all** — there is no supported mechanism ([#175](https://github.com/Sassy-Dog/skills/issues/175)), so the clause is the only thing making these routines work. A "note the degraded load" sentence is discretionary and **has already been dropped in a live run**, which then delivered a complete, authoritative-looking report with no note: a missing sentence reads as fine, an empty slot in a structured header reads as broken. So both report skills render an always-present `Load: plugin | fallback (degraded)` header field and the routine clause names it. **The field is still the run reporting on itself — where the report and the run log disagree, the log wins**; the out-of-band `Unknown skill:` check is [`docs/ROUTINES.md`](docs/ROUTINES.md). Clause shape for any new routine: skill name + its `skills/<name>/SKILL.md` path + the `Load:` field.
- **`work-recommendations` and `work-fire-watch` are dispatch front-ends with one loop between them, and deliberately NO config template.** `work-fire-watch` fetches the newest `daily-fire-watch` post from Slack (read-only, tools resolved by capability, only the pinned poster id counts), reads **only the `fire-watch-v1` machine block** the routine appends — the delivered prose is mrkdwn that changes shape day to day and is never parsed; the producer resolves the product→repo map, so routing is one exact `repo` match — and delegates the numbered list to `work-recommendations`, which resolves each item to a handle, files the issue-less ones through `file-or-link-issue.sh` behind one preview (markers `sentry-source:`, `plate-source:`, `fire-watch-source:` — a closed list), and makes one ordered `take-it` call. Neither has a `.claude/sassy-dog/<name>.md`: both read `take-it.md` only (stopping on `NO_CONFIG` *before* filing anything), so a later "every workflow skill gets a template" sweep should not add one. Nothing pins that absence — a sweep that adds a template *and* its inventory row passes `test-doc-reconciliation.sh` §7 green — which is why it is recorded here. A security finding is human-only in both — the plate's `rotate and revoke` line, and on the fire-watch path the `auto-security-watch` issue that `security-watch.yml` files (the routine's edition has no Security section — its `whats-on-fire` §3E says so, and the block's `security` tier is that edition's "Security, always listed" group; `work-recommendations` reads every `#N`'s live labels before dispatch, and a failed read is HOLD). One approval per run covers filing and dispatch, since neither `take-it` nor `pr-shepherd` asks again. Neither re-runs `whats-on-fire`; a missing or "could not run" post is a stop. **The producer `work-fire-watch` reads is the flattened copy in `routines`** (`Daily Fire Watch (…)`, not this repo's `# What's on fire (…)`); its sentinels and the block spec are listed in [`docs/ROUTINES.md`](docs/ROUTINES.md), `test-fire-watch-block.sh` pins them on this side, and that repo's CI is where a producer-side gate can live (it can clone this one; this one cannot clone it).
- **`setup-config` is a config generator, not a runtime skill.** Run inside a product repo it writes `.claude/sassy-dog/*.md` plus the `.claude/settings.json` plugin declaration, and renders no skill bodies. Modes: **migrate**, **update**, **adopt**, **create**. Siblings `setup-hooks` and `setup-deps` follow the same generator pattern.
- **`setup-repo` is the umbrella orchestrator over those three and carries no generation logic.** It picks which generators apply, prints one combined plan of every file they would touch, gets approval, then runs them **strictly in sequence** (`setup-config` → `setup-hooks` → `setup-deps`) and reports what ran and what was skipped — a skipped generator is a reported outcome, never a silent no-op. **The order is load-bearing**: `setup-config` and `setup-hooks` both write `.claude/settings.json`, merging surgically into their own keys, so sequential runs compose while a concurrent or last-write-wins run drops one *silently* (a prior migration lost a consumer's `PreToolUse` push guard exactly this way). **Never dispatch the generators as parallel sub-agents.** Generation mechanics stay in the generators, **never** in the orchestrator.
- **One delegation mode.** Independent/vendored mode was removed — it was the only path that could produce an unbranded, un-namespaced skill. Everything delegates `Skill: sassy-dog:<cap>`.
- **`setup-hooks` is the same generator pattern one layer down.** It detects the consumer's stack (keyed on repo config presence, never installed binaries) and renders a PostToolUse formatter/linter dispatcher plus an always-rendered stray-artifact guard, with their settings entries. The guard also owns a matcher-less `Stop` entry and ensures `/tmp/` is gitignored — a guard whose destination is not ignored only relocates the mess. **Its two ownership markers behave differently under a rename**: the settings entry is owned by command path (`.claude/hooks/sassydog-`), which no producer rename touches; the script is owned by its `generated-by:` producer name, committed inside every consumer repo — so the matcher must accept every producer name this generator has emitted across both marker namespaces, or every pre-rename script is classified hand-written and skipped *silently*. Re-runs reconcile only owned entries. Pinned by `test-ownership-matchers.sh` and `test-detect-hook-stack.sh`.
- **The two generators' render invariants are deliberately DIFFERENT, and neither should be restated as the other's.** `setup-hooks` stays **deletion-only** — one hook script per repo, so every render is valid by construction. `setup-deps` is **validated after render** ([#169](https://github.com/Sassy-Dog/skills/issues/169)): a Dependabot lane is an (ecosystem, **directory**) pair and a monorepo needs the same ecosystem at several directories, which deletion cannot express — so the template repeats a block per location and `validate-dependabot.sh` asserts every emitted `directory:` actually holds the manifest it claims. That trade is strictly stronger here, because the static guarantee never caught the bug: a bad render was always valid YAML pointing at directories with no manifests, and Dependabot answers that by silently doing nothing. `render-dependabot.sh` refuses to default a lane to `/`, and `--compare-to` catches the diverged-but-owned file rather than overwriting it. Pinned by `test-dependabot-render.sh`.
- **Config format: frontmatter is regenerated, `##` prose is carried across verbatim.** That split is the point — prose is what a refresh must never rewrite. Contract: `setup-config/references/config-contract.md`. **The split assumes frontmatter is *derived*, and several keys are not**; the exceptions are enumerated in `setup-config/SKILL.md`'s guardrail list, which is the copy to trust — do not read this sentence as a closed set. `gotcha_summary` is unbounded free prose in a frontmatter slot, recomputed by nothing, so its rule is **invariants only** — never an issue number with a state claim, an "as of `<date>`", or a roadmap position — enforced where it is *used*: `groom-backlog` injects only what `verify-gotcha-claims.sh` confirms against live issue state (`test-gotcha-claims.sh`). **Marker recognition must accept every producer name and both marker namespaces**; an unrecognised marker drops the repo into create mode and silently loses its config.
- **Write paths are concentrated.** `skills/github-issues/scripts/file-or-link-issue.sh` is the single issue-creation path (marker-keyed idempotency, `--dry-run`, preview-then-confirm, burst rail). That idempotency is **two stages, and neither is redundant** ([#339](https://github.com/Sassy-Dog/skills/issues/339)): the search index is unbounded in *age* but **asynchronous** — a marker re-run seven seconds after filing searched, got `[]`, and filed a duplicate — while a `--search`-less `gh issue list` is a direct object read, read-after-write consistent but bounded to the newest `--recent-scan` issues. **Both stages match the delimited footer `<!-- <marker> -->` through one predicate**, and applying it to one stage is not enough for two different reasons: the scan's `contains()` is a substring test, while GitHub phrase search matches a token *subsequence* — so `epic-split: #207/alpha` hits a sibling `#207/alpha-two`, and the search route fires on the sibling that is already indexed, which is the ordinary case. That harm is quieter than #339's own: a real epic child never filed, reported as `already-linked`. `test-file-or-link-issue.sh` is what stops a later "one lookup is enough" sweep dropping either half. `sentry-triage` never mutates Sentry. Keep it that way.

### Orchestrator + reviewer agents (`assess-it` and `pr-review-orchestrator`)

The nine `*-reviewer` agents have **two dispatchers and two modes**, and the modes are the whole design. Understanding either one means reading its orchestrator alongside the reviewers: `skills/assess-it/SKILL.md` + `orchestration.md` for audit mode, `agents/pr-review-orchestrator.md` for diff-scoped mode.

- **`assess-it` is the audit-mode orchestrator.** Six phases: detect stack → fan out reviewer agents concurrently (one message, multiple Agent calls) → adversarially verify each finding → cluster into PR-sized work → preview and file GitHub Issues under a tracking Epic → report, coverage included. The file numbers them `Phase 0`–`Phase 5`; where the two disagree about labels, trust the file.
- **Audit mode scores a lost reviewer too, and the consequence lands at the PREVIEW rather than in a report** ([#284](https://github.com/Sassy-Dog/skills/issues/284)). This is the **sibling** of the diff-scoped `!` rule, not a copy — and the asymmetry a later "align the two modes" sweep will flatten is the point: a diff-scoped hole is read in-session and costs a re-run, while **audit mode writes**, so a lost `security-reviewer` yields a filed Epic that omits a whole domain and **reads complete** to every later reader. Phase 1 records a four-outcome ledger per domain (`returned` / `no report` / `could not dispatch`, plus `not dispatched` for a domain skipped for cause, kept visibly apart from the two dark ones); a domain that is not `returned` is **dark** and is never scored clean. Phase 4 prints the ledger **before** the approval prompt, Phase 5 reprints it, and **the Epic body carries it too** ([#294](https://github.com/Sassy-Dog/skills/issues/294)) — the durable half, since preview and report are session output reaching only the person who approved the filing. `assessment-rubric.md` carries an **abstain** value, because a table demanding a number from a dark domain makes an agent invent one, and an invented score is worse than a missing one precisely because it looks measured and it sorts. **It is surfaced, not a veto** — filing still proceeds on approval, and both halves are pinned by `test-audit-lost-reviewer.sh`.
- **`pr-review-orchestrator` is the diff-scoped orchestrator** (`agents/pr-review-orchestrator.md`), dispatched by `send-it`'s review gate before the PR body is drafted. It reads the diff versus the *derived* default branch (never an assumed `main`), classifies changed paths into surfaces, fans out **only to touched surfaces**, runs its own integration-check pass for cross-surface concerns no single specialist sees, and returns one report split into **Blocking** vs **Nits**. It dispatches **only the nine reviewers this plugin ships** — the design it replaced named user-level agents, and a plugin default that fans out to an agent a consumer repo lacks fails the entire review rather than degrading, while resolving fine on the author's own machine ([#236](https://github.com/Sassy-Dog/skills/issues/236), pinned by `test-review-orchestrator-allowlist.sh`). Adding a tenth dispatch target means shipping that agent here first.
- **Two config keys carry that gate, and the settled decisions governing it are enumerated in the CI gates section above.** **`review_agent:`** resolves the shipped orchestrator when absent, so no `send-it` run can silently ship unreviewed; the opt-out is the explicit `review_agent: skip`. **`review_site: agent | coordinator`** chooses whether each dispatched sub-agent reviews its own diff **before** opening its PR or the dispatching loop reviews each PR **after** it opens — because `take-it` and `dispatch-ready` open PRs from cold worktrees without invoking `send-it`, and a gate living only in `send-it` never runs for the two paths carrying most of the repo's PR volume ([#248](https://github.com/Sassy-Dog/skills/issues/248)). An absent key selects `coordinator`, for cost: under `agent` every worker ran the full reviewer fan-out itself once per fix round, while every PR is reviewed before merge either way. A repo can steer classification without owning an agent via the optional **`review_surfaces:`** glob → reviewer map ([#238](https://github.com/Sassy-Dog/skills/issues/238)): its values are only those nine, it is **additive** — no form of it removes a reviewer, so it cannot under-dispatch — and an unresolvable value discards the whole map and returns a Blocking finding while the built-in table reviews the diff meanwhile. It steers surface classification alone.
- **A review report is RETURNED as the reviewing agent's final text, never sent to a session** ([#273](https://github.com/Sassy-Dog/skills/issues/273)): delivery needs an address the reviewer cannot reliably resolve, and of five measured occurrences not one report reached the dispatching session — every one that arrived did so because a human relayed it. All three shipping paths read the returned text themselves and never block while a dispatched review is outstanding. A dispatch that ran but produced no usable report is `review: NO REPORT`, never `review: SKIPPED`, which claims no agent ran. `take-it` and `dispatch-ready` hold that PR on either review site; `send-it` records the degraded outcome and continues its operator-facing flow. The reviewer→orchestrator hop is bound the same way ([#280](https://github.com/Sassy-Dog/skills/issues/280)): each of the nine states the full rule, and the delivery rule is a **member** of the fan-out brief, whose list stays **closed** — closedness is what stops a brief re-authoring a reviewer's checklist. None of it retires Step 5's lost-reviewer reporting bullet: a clean fan-out is not evidence the hop worked, so read the `!` count.
- **Parent recovery belongs only to the shipped PR orchestrator** ([#385](https://github.com/Sassy-Dog/skills/issues/385)); its single definition is `### Parent recovery protocol` in `agents/pr-review-orchestrator.md`. Normal nested fan-out stays the default. Explicit plan-only or inability to dispatch nested reviewers returns a `review-fanout-plan`, not a report; only the actual caller can run a missing/unusable-only concurrent batch and submit complete actual returns and failures to `aggregate-only`. Changeset/context identity gates every reuse, and aggregation still performs the whole-diff integration pass without rerunning successful specialists. The batch plus aggregation shares the existing single automatic recovery allowance with failed checks and Blocking findings.
  **Report-only recovery** ([#386](https://github.com/Sassy-Dog/skills/issues/386)) uses that same allowance at most once when the shipped orchestrator returned only a correction, tally or partial text: normal and compact-clean reports are already complete. With identical changeset/context and the actual returned dispatch handle/agent identity, the caller may request only the already-completed full human report, never re-analysis, fan-out, an integration pass, a relay or file pointer. It retains enumerated Blocking findings and dark coverage unless that full report explicitly supports their correction; changed input, an unreachable handle, spent/unknown allowance or another fragment stays NO REPORT, never clean.
  Recovery accounting accepts only authenticated workflow-owned records bound to the actual attempt. `send-it` defines a branch-keyed checkpoint under the Git common directory for pre-PR work with no linked issue, then transfers its state into the PR body; `dispatch-ready` persists pending reservations before the scheduling tick ends.
  Exhausted pre-PR failures use `take-it` §5's authenticated issue-only terminal handoff. Both coordinators consume it before PR filtering; active-attempt identity prevents stale demotions, and only confirmed blocking frees capacity. Absence of a PR or spent recovery alone is never a terminal outcome.
- **The `*-reviewer` agents are the fan-out workers for both.** Each owns a domain (architecture, code-quality, security, testing, cicd-release, infra-platform, observability-ops, dx-docs, dependency-supply-chain) and in **either** mode it FINDS problems and cites `file:line` evidence, never writing code. Audit mode sweeps the repo and asks "what is wrong here"; diff-scoped mode is handed a changeset and asks "does this diff introduce a regression", bounded to the changed hunks and their blast radius. The audit dispatch map lives in `orchestration.md`, the diff-scoped surface map in the orchestrator. Each reviewer's `## Diff-scoped mode` section is a sibling of its audit-mode declaration, not a replacement.
- **All agents return the same finding schema in BOTH modes** (title, area, severity, likelihood, evidence, why_it_matters, proposed_fix, acceptance, pr_size, labels, confidence). The return transport is the JSON object `{"findings": [...]}`; `{"findings": []}` is a completed empty review, and missing or malformed envelopes are unusable, never clean. One transport form beyond a bare object is usable: exactly one fenced block (` ```json ` or bare ` ``` `) with only whitespace outside it, held to the same schema check; prose outside the object, two or more fences and an unterminated fence stay unusable, identically in both consumers. Reviewers must still return a bare object; the tolerance exists only so a completed review is not discarded. Both consumers unwrap the array; the final human PR report stays Markdown. That is what lets one set of reviewers serve two orchestrators, so it is the invariant to protect: keep any edit to one reviewer's output contract consistent with `orchestration.md` and the others, and never let a mode grow a field of its own. Blocking-vs-Nits is a *derivation* the PR orchestrator performs from `severity`, `confidence` and a policy citation the finding's own `evidence` carries — reviewers do not pre-split, and the orchestrator never promotes on an impression the schema cannot express.
- `github-secrets` and `testflight` are standalone capability skills — no agent orchestration.

## Conventions that matter

- **`whats-on-fire`'s rules carry parity markers, and the CI gate for them is in the OTHER repo.**
The skill has two intentional homes: this plugin copy (`SKILL.md` + `references/`) and the
flattened, self-contained copy in `Sassy-Dog/routines` that the `daily-fire-watch` cloud
routine reads by path, which exists because plugin skills cannot load in a routine session
([#175](https://github.com/Sassy-Dog/skills/issues/175)). Nothing used to check that the
two agreed, and on 2026-08-20 that produced a false P0 in the scheduled run — **a fix applied to
this copy would not have changed the routine's behaviour at all** ([#221](https://github.com/Sassy-Dog/skills/issues/221)).
Every load-bearing rule now carries a `<!-- rule: <id> -->` marker beside it in *both* homes, and
`routines`' `scripts/check-skill-parity.sh` fails when the marker sets differ. **Adding a
rule here means adding the marker here, the marker there, and a line in that repo's
`parity/whats-on-fire-rules.tsv`.** Two things not to redesign: the check compares marker
*identity* and never prose, because the two homes word the same rule differently and wrap it
differently — a wording-based check reports the routine as missing rules it plainly carries; and it
cannot move into this repo, because this repo is PUBLIC and that one is INTERNAL, so its CI can
clone this one anonymously while this one's CI cannot authenticate to it at all (the
`private`-visibility trap of [#178](https://github.com/Sassy-Dog/skills/issues/178)). A
change spanning both repos lands **here first**, or that repo's CI clones a `main` without the new
marker and fails.
The stale-verdict section ([#375](https://github.com/Sassy-Dog/skills/issues/375)) renders
the existing `ci-verdict-age-bound` rule, whose marker was added in
[#379](https://github.com/Sassy-Dog/skills/pull/379); it does not introduce another rule
identity. Its marker counterpart was reconciled in
[routines#60](https://github.com/Sassy-Dog/routines/issues/60); that marker-only
change does not establish parity of the rendering instructions.
- **Every dispatch site names a tier, bound inline where the agent is dispatched.** Tiers are harness-neutral words (`astra`/`sol`/`terra`/`luna`), because the skills must port beyond Claude Code and no single `model:` value is valid in two harnesses. The binding table is [`docs/MODEL-TIERS.md`](docs/MODEL-TIERS.md), and agent files carry **no** `model:` frontmatter. Implementation workers and the nine reviewers run at `terra`; the orchestrator runs at `sol`. A dispatch site that names no tier silently inherits the session model, which is how implementation and review both ended up on the most expensive tier. `test-model-tiers.sh` counts each site's binding and checks it against the table. Its `required` table is the enumerated site list, so a new dispatch site joins that table in the same PR.
- **Skill `description` is a trigger spec, not a summary.** It is dense with quoted user phrases ("set a GitHub secret", "check TestFlight feedback") because matching those phrases is what activates the skill. When adding/editing a skill, write the description as the list of utterances that should trigger it.
- **Progressive disclosure.** SKILL.md stays thin and actionable; depth goes in `references/*.md` that the skill says to read "when you reach that phase." Don't inline reference-doc detail into SKILL.md.
- **`${CLAUDE_PLUGIN_ROOT}` expands only in `SKILL.md`, at load time.** It is NOT substituted in `references/*.md` and is not a shell variable, so a reference doc or a bundled script that writes the token raw emits it literally and the path silently fails to resolve. A reference doc must take the already-resolved absolute path from the `SKILL.md` that invoked it. The thirteen reference-doc commands that wrote the token raw were repointed in [#329](https://github.com/Sassy-Dog/skills/issues/329): each doc now opens with a **path-resolution preamble** setting `PLUGIN_ROOT`, and its commands quote `"$PLUGIN_ROOT/..."`. `test-plugin-root-in-references.sh` keeps it that way — it bans the token in COMMAND usage (keyed on fenced code blocks) while deliberately sparing the prose in `skills/assess-it/references/github-issue-ops.md` that documents the trap, and it fails a doc that uses `$PLUGIN_ROOT` without defining it, since an unset variable resolves against `/` exactly like the token did. **The one place a SKILL.md must NOT spell the token** is the root-resolution paragraph ([#454](https://github.com/Sassy-Dog/skills/issues/454)): every `SKILL.md` that carries the token also carries one paragraph before the first fenced command that uses it, for harnesses (omp) that neither substitute nor export it, and Claude Code substitutes the token anywhere in a `SKILL.md`, so a paragraph that spelled it would be rewritten into a path inside its own sentence. It says "the plugin-root placeholder" instead. `test-plugin-root-paragraph.sh` pins the text, the placement and the token-freedom; the text is the wording that passed on omp, so change it only with a re-run.
- **A count stated in prose is safe only when its members are enumerated beside it, or when a gate re-derives it.** A bare number with neither support rots silently — nothing fails when it stops being true, which is the whole reason #268/#276/#278 exist. Several gate headers defer to this rule by name rather than restating it (`test-drain-terminal-states.sh`, `test-audit-lost-reviewer.sh`), so it must keep a home here.
- **Reviewer agents carry a "Sassy Dog calibration" section** applied only when the relevant stack is present (e.g. Doppler is the secrets source of truth, all-secrets/zero-`vars.*`, managed identity + Key Vault `kv-sassydog`, pin Actions to SHAs). New org-wide policies belong in the matching reviewer's calibration block.
- **No bare `$1`–`$9`/`$@`/`$*` in SKILL.md bodies or dev-workflow templates.** Skill bodies are arg-substitution surfaces: when a skill is invoked with args (as every thin generated skill invokes its capability skill), positional tokens in the rendered body get replaced with args tokens, corrupting embedded commands. CI greps for them (`skills/*/SKILL.md`, `.claude/skills/*/SKILL.md`, `setup-config/references/templates/*`). The guard now asserts that template pathspec is non-empty first — an empty pathspec used to make it pass while covering nothing. Use `cut -f1`/`%(format)` idioms instead, or move the snippet to a `references/` doc or bundled script — neither is substituted.
- **Outward-facing actions require preview-then-confirm.** `assess-it` never files GitHub Issues silently — it prints the full Epic + child-issue preview and files only on approval. Preserve this guard in any change.
- **Irreversible actions are gated structurally, not by ordering.** `scripts/align-labels.sh --migrate` folds a repo's one-off labels onto the canonical set, and deleting a label strips it from every issue carrying it unrecoverably. "Relabel first, delete second" is therefore control flow, not a comment: `gh label delete` has exactly ONE call site, inside `migrate_delete_gate()`, whose own body re-queries GitHub immediately above it and returns without deleting on every path that is not "zero issues still carry the old label" — **including "the re-query itself failed", because unknown is not verified**. The relabel loop's counters are not a parameter of that function; the migration's own success message is never the evidence. Pinned by `test-label-migrate.sh`, which asserts the single-call-site invariant against the source and mutation-proves the gate. Any new destructive capability goes behind the same shape: one call site, its own fresh verification in the same body.
- **A taxonomy consumer runs the owner or reads its `taxonomy` emitter — it never transcribes the table.** Two tables exist: `scripts/align-labels.sh` (10 engineering dimensions + 4 severities) and `skills/github-issues/scripts/issue-claim.sh` (the 4 dev-workflow state labels). Each exposes `taxonomy` (`name|color|description`; no gh, jq, repo or network), and each reads the other through it — that is how `--collisions` scores both sets without a copy. `assess-it` was the counter-example: a third transcription in a reference doc, frozen at pre-#158 colours, so recolouring `tech-debt` created a collision *inside a file that change never saw* and shipped into every repo it audited ([#167](https://github.com/Sassy-Dog/skills/issues/167)). It now invokes `align-labels.sh --repo <target>`; `test-label-taxonomy.sh` fails on any taxonomy colour found outside its home.
- Conventional commits (`feat:`, `fix:`, `chore:`, `docs:`). Recent history uses PRs to `main`.

## Local development

```bash
# Run Claude Code with this plugin loaded from the working tree
claude --plugin-dir ~/Repos/sassy-dog/skills

# Install from the published marketplace
claude plugin marketplace add Sassy-Dog/skills
claude plugin install sassy-dog
```

After editing a skill or agent, reload via `--plugin-dir` and invoke the skill to confirm frontmatter parses and triggers fire.

## Releasing

The plugin version is **monthly-rolling CalVer** (`YYYY.M.<commits-this-month>`, e.g. `2026.7.16`) per the org Versioning spec; the committed `version` in `.claude-plugin/plugin.json` is the version-of-record. **Never hand-edit it** — stamp it:

```bash
bash scripts/stamp-version.sh   # resolves CalVer and writes .claude-plugin/plugin.json
```

Commit the stamped manifest in the release PR. Build number: N/A for this repo; tags optional. Full instance doc — including the **one-way ratchet** (no `0.x`/`1.x` may ever follow CalVer): [`docs/VERSIONING.md`](docs/VERSIONING.md). Keep `README.md`'s plugin/skill table, the agent list and the `### Harness support` matrix in sync when skills or reviewer agents are added or removed.
